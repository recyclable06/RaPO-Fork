# LoRA 分片同步的必要检查与运行观察

更新日期：2026-11-01。状态：原版在两卡 task5 同步合并 OOM；新的分片同步代码已实现，本地 CPU 检查通过，待用户在集群运行验证。

配套：[设计文档](design.md)、[决策记录](decisions.md)。本次交付是一版降低同步峰值的实现，用户负责集群尝试。本文只覆盖此次改动直接影响的业务，不是完整 LoRA 复现的验收清单。

## 1. 本次关注三件事

| 检查 | 最小做法 | 为什么必须做 |
|---|---|---|
| 分块合并保持有效权重含义 | 用非零 LoRA 增量和更新后的向量，将小模型或小张量的分块结果与原合并公式比较，涵盖 Linear、Embedding、Conv3d 和共享 head | 防止转置、分块边界、遗漏向量或重复增量错误 |
| vLLM 收到新的有效权重 | 结合加载逻辑和必要的局部权重核对，运行“生成—更新—重新同步—生成” | 防止能运行但仍用旧权重；不依靠随机答案相同证明正确 |
| Anchor 正确接收上一任务权重 | 在实际任务切换中核对新写回路径的名称、分片布局与必要数值，并继续下一任务 | 这是本次改动的主要分布式难点，不能只看加载函数是否返回 |

局部数值比较考虑 BF16 舍入，不要求不同后端位级一致。只为完成这些检查选择够用的做法，不同时要求权重全量比对、跨后端输出比对和整模型快照；也不为检查构造真实模型的完整 GPU 权重副本。

已有 `tests/test_full_lora.py` 可复用或作小幅调整，验证新增合并逻辑；不另建测试框架，不预设测试数量或覆盖率。必要的名称/形状检查与 Anchor 的 `strict=True` 直接保障权重正确装载，保留即可，不扩展成审计系统。

本次在该文件新增一项分块同步数值检查，测试共 3 项通过。新增检查使用非零增量、更新后的向量和非整除行块，比较 FP32/BF16 的 Linear、Embedding、Conv3d、共享 head 与原公式，并检查 Actor 不变、普通 CPU 张量的 Anchor 名称/形状和一次状态写回。运行命令仍为 `python -m unittest discover -s tests -p test_full_lora.py -v`。该结果不包含 CUDA DTensor 聚合/重分片或 vLLM 实际加载，真实峰值、RAM 和耗时尚未测量。

原实现的微型模型 CPU 检查已通过，两卡也实际运行过四个任务；这些不代表新分片路径已验证。本次不改参数注入、优化器、Ref、CTAN 或 checkpoint，没有相应改动或故障时，不重新组织逐参数梯度、全模型隔离快照、保存重载和恢复检查。

## 2. 交付后由用户尝试运行

实现完成并做与改动相称的本地检查后交给用户；明确本地 CPU 检查无法确认 CUDA/FSDP/vLLM 的实际行为。用户复用现有入口，按可用资源和实验需要选择卡数、超参数与运行长度。重新同步和任务切换可由同一次实际运行覆盖，不要求先跑独立两卡探针，也不要求为此编写短跑控制器。

先尝试降低峰值；速度、RAM 和显存表现根据已有监听数据分析，不设门槛或规定资源报告。已有数据不足以解释具体问题时，再补最少的定位信息。

是否继续完整 10-task、增加 seed、运行 20-task 或调参，由实际结果决定，不属于本次实现交付要求，也不要求先跑完一轮才能调整学习率。

## 3. 后续实验如何解释结果

对照需要说明模型起点、任务与数据设置、评估口径及训练配置差异，不要求 LoRA 逐项沿用全参数更新的超参数。学习率、rank/alpha、batch、rollout 数量和训练轮数等可以按 LoRA 的实际学习效果与资源情况调整，记录在现有配置中即可。数据或评估设置有变化时，解释其对结果可比性的影响。

学习率提高约 10 倍是师兄提出的候选建议，可以试验；例如以现有 `1e-6` 为参照，可尝试 `1e-5`。这不是固定倍率或已验证的最优值，也不要求先用原学习率跑完整序列。后续依据学习效果、遗忘和训练稳定性选择，不预设一套参数搜索流程。

训练配置的差异应随结果说明；一个 seed 只形成初步结论。模型、量化或并行方式的进一步改造不属于本次同步实现。

已有结果足以提供的主要比较项：最终 `last_acc`、`forgetting_rate`、每任务准确率矩阵，以及完成时间。任务矩阵可同时反映新任务是否学会、旧任务是否遗忘，无需另造指标系统。`average_acc` 不与最终准确率混用。
